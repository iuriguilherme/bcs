# Dead method on wrong class, redundant type guard, and stale production bundle

Discovered during a multi-agent code review (PR #6). Three distinct issues in the molecule-intent system, all fixed in a single commit (`7f1a4fb`).

## Symptoms

- `Environment` class had a `_rule1_repelIrrelevantAtoms` method — silently unreachable
- `Intention.update()` had a nested `if (this.type === 'molecule')` inside an identical outer guard — dead `else` branch
- T04 (`t04-polymer-intent.spec.js`) passed in 7s on `dev.html` but timed out after 3 minutes on `index.html`

## Root Cause Analysis

### Issue 1: Dead method on wrong class

`Environment._rule1_repelIrrelevantAtoms(environment, state)` was a copy-paste artifact left behind when molecule-intent logic was migrated from `Environment` to `Intention`. The real implementation was already on the `Intention` class (line 478 of `intention.js`) and was being called correctly. The `Environment` copy was never wired to any call site.

The orphaned method had four compounding bugs — none caught because it was never executed:

1. **Wrong state property**: Called `this.getIntentionForAtom(state.atom)` but `state.atom` doesn't exist. The `_buildState()` method produces `nearbyAtoms`, `targetComp`, `claimed`, `free`, etc. — not `atom`. `intention` was always `undefined`.

2. **Guard inside loop**: `if (!intention) continue` was inside the `for` loop, not before it. Since `intention` was always `null` (from bug #1), every iteration O(n) wasted checking a constant.

3. **Inverted force direction (attract vs. repel)**:
   ```js
   // BUG: points TOWARD intention center — this is attraction, not repulsion
   atom.applyForce(new Vector2(
       intention.position.x - atom.position.x,
       intention.position.y - atom.position.y
   ));
   // CORRECT: atom.position - intention.position (outward vector)
   ```

4. **Naming convention violation**: The `_rule1_*` prefix is a class-scoped convention that belongs exclusively to `Intention`. Any method with this prefix on `Environment` is a category error — it pollutes the convention and would mislead future debugging.

### Issue 2: Redundant nested type guard

Inside `Intention.update()`, the outer `if (this.type === 'molecule')` block already guaranteed `type === 'molecule'` for everything inside it. An inner identical guard was never removed when the outer one was added during refactoring:

```js
// BEFORE — dead inner guard
if (this.type === 'molecule') {
    this._validateSeed(environment);
    const state = this._buildState(environment);
    if (this.type === 'molecule') {  // ← always true — dead guard
        this._rule1_repelIrrelevantAtoms(environment, state);
        // ... rules 2–7
    } else {
        // ← unreachable — dead else branch
        this._attractComponents(environment);
        this._checkCompletion(environment);
    }
} else {
    this._attractComponents(environment);
    this._checkCompletion(environment);
}
```

A reader encountering the inner `else` could waste time reasoning about a case where `type === 'molecule'` leads to `_attractComponents` — which can never happen.

### Issue 3: Stale production bundle

`index.html` is a pre-built bundle generated by `deno run build.ts`. Source changes to `intention.js` were made and tested against `dev.html` (which loads scripts directly from `src/`). The bundle was not rebuilt. T04's polymer intent test depends on the corrected `Intention.update()` logic — running against the old bundle, the simulation never reached the expected state within 120 seconds.

The asymmetry (`dev.html` passes in 1.3 min, `index.html` times out at 3 min) is the canonical symptom of a stale bundle. When you see this pattern, rebuild first before investigating further.

## Solution

### 1. Delete the dead method from `Environment`

Removed `Environment._rule1_repelIrrelevantAtoms` (lines 932–953 of `environment.js`) entirely. The live implementation on `Intention` was already correct and in use.

```diff
-    /**
-     * Rule 1: Repel atoms not in the target molecule composition
-     * Atoms outside the blueprint are strongly repelled to prevent wrong molecules forming.
-     */
-    _rule1_repelIrrelevantAtoms(environment, state) {
-        const intention = this.getIntentionForAtom(state.atom);
-        ...
-    }
-
     /**
      * Get all atoms as array
      */
```

### 2. Flatten the redundant inner guard in `Intention.update()`

```js
// AFTER — clean, flat structure
if (this.type === 'molecule') {
    this._validateSeed(environment);
    const state = this._buildState(environment);
    this._rule1_repelIrrelevantAtoms(environment, state);
    this._rule2_repelIrrelevantMolecules(environment, state);
    this._rule3_claimFreeAtoms(environment, state);
    this._rule4_extractFromMolecules(environment, state);
    this._rule5_attractClaimed(environment, state);
    this._rule6_bondClaimed(environment, state);
    this._rule7_checkCompletion(environment, state);
} else {
    // polymer / cell intents
    this._attractComponents(environment);
    this._checkCompletion(environment);
}
```

### 3. Rebuild the production bundle

```bash
deno run --allow-read --allow-write --allow-run build.ts
```

Commit `index.html` alongside the source changes. These are never separate commits.

## Verification

```bash
npx playwright test t04
# ✓ [dev] T04: polymer intent (6.7s)
# ✓ [prod] T04: polymer intent (7.3s)
```

Both dev and prod passed in under 8 seconds. Previously prod timed out at 3 minutes.

## Prevention

### Naming convention: `_rule1_*` is class-scoped to `Intention`

The `_ruleN_` prefix is an established convention that belongs **exclusively** to `intention.js`. Any method with this prefix on any other class is a bug.

```bash
# This should return zero results — enforce in code review
grep -rn "_rule[0-9]" src/ | grep -v "intention.js"
```

Document this at the top of `intention.js`:
```js
// _ruleN_ methods are canonical here. Do not define them elsewhere.
// Rule numbering is sequential and never reused after deletion.
```

### Refactoring hygiene: delete the source when moving logic

When moving a method from one class to another, delete the original in the same commit. Two implementations of the same concept coexisting is always a bug.

After any method-move refactoring, verify before committing:
```bash
grep -r "oldMethodName" src/  # should return zero after move
```

### Catching redundant guards

When adding an outer conditional that makes an inner one redundant, remove the inner one in the same PR. ESLint's `no-dupe-else-if` and `no-constant-condition` rules catch some of these patterns. For manual review: any `if (X) { if (X) { ... } else { ... } }` requires justification.

### Mandatory bundle rebuild before prod tests

**If `dev.html` passes but `index.html` times out → rebuild the bundle first.** Don't investigate physics.

To prevent this entirely, add a `pretest` script to rebuild automatically:
```json
// package.json
"scripts": {
    "pretest": "deno run --allow-read --allow-write --allow-run build.ts",
    "test": "playwright test"
}
```

Or add a bundle freshness assertion to the Playwright prod fixture:
```js
// Fails immediately if bundle is stale instead of silently timing out
const buildTime = await page.evaluate(() => window.__buildTime);
expect(Date.now() - buildTime).toBeLessThan(5 * 60 * 1000); // < 5 min old
```

### Force vector sign check

Any method computing a repulsion force must have the vector direction verified:
- **Attract**: `center - atom` (points toward center)
- **Repel**: `atom - center` (points away from center)

A quick sign check: if the force is supposed to push atoms outward and you see `intention.position - atom.position`, the sign is wrong.
